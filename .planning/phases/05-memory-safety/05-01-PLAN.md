<task type="auto">
  <name>Task 1: Fix preprocessing() realloc-to-zero leak</name>
  <files>cbqs/src/constraint.c</files>
  <action>
Fix the memory leak in preprocessing() at lines 209-210 where realloc(ptr, 0) is called when array_length is 0.

**Pattern to apply:**

Replace:
```c
con->positive_indices = realloc(con->positive_indices, con->positive_array_length * sizeof(uint32_t));
con->negative_indices = realloc(con->negative_indices, con->negative_array_length * sizeof(uint32_t));
```

With:
```c
if (con->positive_array_length == 0) {
    free(con->positive_indices);
    con->positive_indices = NULL;
} else {
    uint32_t *new_pos = realloc(con->positive_indices, con->positive_array_length * sizeof(uint32_t));
    if (new_pos != NULL) {
        con->positive_indices = new_pos;
    }
    /* If realloc fails, keep original (over-allocated but not leaked) */
}

if (con->negative_array_length == 0) {
    free(con->negative_indices);
    con->negative_indices = NULL;
} else {
    uint32_t *new_neg = realloc(con->negative_indices, con->negative_array_length * sizeof(uint32_t));
    if (new_neg != NULL) {
        con->negative_indices = new_neg;
    }
}
```

Apply the same fix to preprocessing_sparse() at lines 347-348.

**Why this pattern:** realloc(ptr, 0) has implementation-defined behavior (C11 7.22.3.5). On some platforms it returns NULL and frees the memory; on others it returns a non-NULL pointer that cannot be freed. Explicit free() is always correct.

Create a Valgrind suppression file to filter known benign leaks from Python, numpy, and Cython runtime.

**File content:**
```
# Valgrind suppression file for Python/numpy/Cython
# These are known benign allocations that persist for interpreter lifetime

# Python allocator false positives
{
   PythonMalloc
   Memcheck:Leak
   ...
   fun:PyObject_Malloc
}

{
   PythonRealloc
   Memcheck:Leak
   ...
   fun:PyObject_Realloc
}

{
   PythonCalloc
   Memcheck:Leak
   ...
   fun:PyObject_Calloc
}

# Python GC and internal allocations
{
   PythonGC
   Memcheck:Leak
   ...
   fun:_PyObject_GC_*
}

{
   PythonArena
   Memcheck:Leak
   ...
   fun:PyArena_*
}

# Python type/module initialization
{
   PythonTypeInit
   Memcheck:Leak
   ...
   fun:PyType_Ready
}

{
   PythonModuleCreate
   Memcheck:Leak
   ...
   fun:PyModule_Create*
}

# NumPy initialization leaks (benign)
{
   NumpyInit
   Memcheck:Leak
   match-leak-kinds: possible
   ...
   obj:*/numpy/*.so
}

{
   NumpyUFunc
   Memcheck:Leak
   ...
   fun:*ufunc*
   obj:*/numpy/*.so
}

# Cython generated code
{
   CythonPyxImport
   Memcheck:Leak
   ...
   fun:__pyx_*
}

{
   CythonModuleInit
   Memcheck:Leak
   ...
   fun:PyInit_*
   obj:*/cbqs/*.so
}

# Python thread state
{
   PythonThreadState
   Memcheck:Leak
   ...
   fun:PyThreadState_*
}

{
   PythonGILState
   Memcheck:Leak
   ...
   fun:PyGILState_*
}

# Standard library leaks
{
   PythonImport
   Memcheck:Leak
   ...
   fun:PyImport_*
}
```

**Why these suppressions:** Python's memory allocator maintains object pools that appear as "leaks" to Valgrind because they persist for interpreter lifetime. NumPy and Cython have similar patterns. These are well-documented false positives.
